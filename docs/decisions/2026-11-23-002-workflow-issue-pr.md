# 작업 흐름: 이슈 → 브랜치 → PR

> **한 줄 이유:** 이슈 단위로 나누면 진행 상황이 보이고, 언제든 협업자에게 작업을 넘길 수 있다.

- 날짜: 2026-11-23
- 이슈: #2
- PR: #6
- 회의록: [2026-11-23 프로젝트 킥오프](../meetings/2026-11-23-kickoff.md)
- 상태: 채택 (스택 금지로 보완 → [014](2026-11-23-014-no-stacked-prs.md))

## 배경

혼자 하는 프로젝트지만 언제든 협업으로 바뀔 수 있어야 하고, 진행 상황은 GitHub Project에서 볼 수 있어야 한다.

## 결정

- 모든 변경은 먼저 이슈로 등록하고, **이슈 하나당 PR 하나**로 처리한다.
- 브랜치 이름: `<type>/<이슈번호>-<설명>`
- 커밋: Conventional Commits (`<type>: <요약> (#이슈)`)
- PR 본문에 `Closes #N`을 적고, Squash merge 후 브랜치를 삭제한다. main에 직접 push하지 않는다.
- 라벨: 종류(`type: *`)와 단계(`phase: MVP` / `phase: post-MVP`)
- 이슈는 폼 템플릿(기능/버그/작업)으로만 만들고 빈 이슈는 막는다.
- MVP를 먼저 구현하고, 상세 기능은 post-MVP 이슈로 쌓아둔다.

## 이유

- 이슈 단위로 끊으면 Project 보드에서 진행 상황이 그대로 보이고, 협업자에게 작업을 넘기기 쉽다.
- Squash merge를 하면 main 히스토리가 "이슈 1개 = 커밋 1개"가 되어 추적이 쉽다.
- 라벨을 두 축으로 나누면 "지금 MVP에 필요한 것"만 따로 걸러 볼 수 있다.

## 영향

- 작은 수정도 이슈를 거쳐야 하므로 절차 비용이 있다. 일관성을 위해 감수한다.
