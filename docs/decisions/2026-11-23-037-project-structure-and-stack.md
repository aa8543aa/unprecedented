## 1. MVP 정의

자전거를 타는 사람이 **지금 속력으로 무언가와 정면 충돌하면 나와 상대가 얼마나 다치는지**를 백미러 화면 위에서 바로 보는 것. 이 흐름이 동작하는 데 꼭 필요한 것만 넣었다.

| 이슈 | 기능                 | 왜 MVP인가                                 |
| ---- | -------------------- | ------------------------------------------ |
| #22  | 부상도 계산 모듈     | 앱의 핵심 숫자. 없으면 화면이 의미 없음    |
| #23  | 주행 전 설정         | 몸무게·자전거·헬멧이 계산 입력값           |
| #24  | 주행 화면 UI         | 확정된 디자인 그 자체                      |
| #25  | GPS 속력 (+슬라이더) | 속력이 입력의 중심. 슬라이더는 시연·실내용 |
| #18  | 카메라 백미러 배경   | 디자인에서 화면 바탕이 백미러로 정해짐     |

뺀 것(post-MVP): 경사도(#26, 속도와 이중 계산 위험), 사고 확률(#27, 근거 약함), 25km/h 기준선(#28), 주행 기록(#29), 정적 배포(#30), APK(#31). 없어도 핵심 흐름이 동작한다.

## 2. 프로젝트 구조

```
src/
  engine/      부상도 계산. 화면과 기기를 모름 (순수 함수 + 인터페이스)
    types.ts     입력/출력 타입, RiskEngine 인터페이스
    data.ts      상수와 출처 (대상·자전거 프리셋, 헬멧 보정, 전치 기준표)
    model.ts     Δv, 부상도 곡선, 단계 변환, evaluateRisk
    index.ts     localEngine (브라우저 안 계산)
    useRisk.ts   화면이 계산 결과를 받는 유일한 통로
  sensors/     기기 센서. 화면을 모름
    speed.ts       좌표 거리, 속력 계산, 평활
    useGpsSpeed.ts 위치 API 훅과 상태
    camera.ts      카메라 조건과 오류 상태
    useRearCamera.ts 카메라 영상 훅
  settings/    주행 전 설정의 타입, 기본값, 저장(localStorage), 값 검사
  screens/     화면
    SetupScreen      주행 전 설정
    ride/RideScreen  주행 화면 (배경·조작부를 바깥에서 받음)
    ride/PartyGauge  좌우 부상도 막대
    ride/CameraBackground 백미러 배경
    ride/RideContainer    센서를 주행 화면에 연결
  App.tsx      설정 ↔ 주행 화면 전환
```

**왜 이렇게 나눴나**

- **바뀌는 이유가 다르다.** 계산식은 연구 데이터가 바뀌면, 센서는 기기·브라우저가 바뀌면, 화면은 디자인이 바뀌면 고친다. 한 파일에 섞으면 하나를 고칠 때 다른 것이 깨진다.
- **서버로 옮길 수 있게.** 화면은 `useRisk`와 `RiskEngine` 인터페이스만 안다. 서버 계산으로 바꿀 때는 `RiskEngine`의 원격 구현을 만들어 넘기면 되고, 화면은 그대로다. ([앱 형태와 연산 위치](2026-11-23-004-web-app-local-compute.md)의 결정)
- **테스트하기 쉽게.** 계산(`model.ts`), 속력 계산(`speed.ts`), 설정 검사, 카메라 조건은 브라우저 없이 순수 함수로 테스트한다. 테스트 22개.
- **센서와 화면 분리.** `RideScreen`은 속력 숫자와 배경을 받기만 한다. GPS·카메라는 `RideContainer`가 붙인다. 그래서 #24(화면)를 먼저 만들고 #25(GPS), #18(카메라)을 나중에 붙일 수 있었다.

## 3. 기술 스택

| 항목   | 선택                                   | 이유                                                                               |
| ------ | -------------------------------------- | ---------------------------------------------------------------------------------- |
| 언어   | TypeScript 6                           | 계산 입력/출력 타입이 많아 실수를 컴파일 때 잡음                                   |
| UI     | React 19                               | 처음부터 쓰던 스택. 화면 상태가 단순해 기본 기능(useState, useEffect)만으로 충분   |
| 빌드   | Vite 8                                 | 개발 서버가 빠르고, 빌드 결과가 정적 파일이라 서버 없이 배포 가능                  |
| 테스트 | vitest 4                               | Vite 설정을 그대로 씀. 추가 설정이 거의 없음                                       |
| 스타일 | 일반 CSS + CSS 변수                    | 화면 2개라 프레임워크가 필요 없음. 색 토큰(부상 단계 색 등)을 변수로 한곳에서 관리 |
| 폰트   | Noto Sans KR, Space Grotesk            | 한글 가독성, 숫자는 폭이 고른 글꼴로 속력·%가 흔들리지 않게                        |
| 저장   | localStorage                           | 설정 4개뿐. 서버 없음. 못 쓰는 환경에서는 기본값으로 동작                          |
| 속력   | 브라우저 Geolocation API               | 설치 없이 웹에서 바로. 기기 속력이 없으면 좌표 거리/시간으로 계산                  |
| 카메라 | 브라우저 getUserMedia                  | 설치 없이 웹에서 바로. 전면/후면 선택                                              |
| 품질   | ESLint + Prettier, husky + lint-staged | 기존 설정 그대로 ([001](2026-11-23-001-eslint-prettier.md))                        |

**쓰지 않은 것과 이유**

- **라우터(react-router 등):** 화면이 2개뿐이라 `App.tsx`의 상태 하나로 전환한다.
- **상태 관리 라이브러리(Redux, Zustand 등):** 공유 상태가 설정 하나뿐이다.
- **CSS 프레임워크(Tailwind 등):** 디자인이 고정되어 있고 화면이 작다. 의존성을 늘릴 이유가 없다.
- **차트 라이브러리:** 막대 하나는 CSS 높이로 충분하다.
- **서버:** 계산이 가볍고, 위치 정보를 기기 밖으로 보내지 않는 편이 낫다.

## 영향

- 실기기에서 GPS 속력과 카메라 영상은 아직 확인하지 않았다. HTTPS 배포(#30) 후 확인한다.
- 계산 상수는 과제 수준의 근사값이다. 바꿀 때는 `src/engine/data.ts`만 고치면 되고, 출처를 주석에 남긴다.
- 화면이 늘어나 전환이 복잡해지면 라우터 도입을 다시 검토한다.
